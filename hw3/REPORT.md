# 安心搜尋（SafeSearch）專案報告

## 摘要

本專案以 Node.js 內建模組實作一個「不受使用者偏好影響排序」的搜尋引擎示範，命名為「安心搜尋（SafeSearch）」。系統的核心設計有兩個：

1. **非個人化排序**：搜尋結果只由查詢字詞與文件內容決定，使用 TF-IDF 餘弦相似度排序；同分時依文件編號排序。使用者的偏好設定、瀏覽紀錄、位置、裝置與身分都不會進入排序函式。
2. **敏感搜尋的即時關懷**：當查詢包含自殺、自我傷害、傷害他人、嚴重情緒困擾或身體健康困擾等關鍵字時，系統會先顯示關懷頁面與求助資源（1925、1995、1980、113、119、110），而不是一般搜尋結果。使用者確認後仍可查看結果，但關懷提示會保留在結果頁上方。

本專案不依賴任何第三方套件，可直接以 `node server.js` 啟動，並以 `node --test` 執行 25 項自動化測試。

> 本系統為現代軟體工程課程的教學示範，不提供醫療診斷或危機處理的專業服務。若你或身邊的人正處於立即危險，請立刻撥打 119 或 110。

## 1. 專案簡介

### 1.1 背景與動機

現代搜尋引擎與內容平台常依使用者偏好、歷史行為、位置與互動訊號進行個人化排序。個人化能提升點擊率，但也可能造成：

- 不同使用者搜尋同一個問題，卻看到不同的事實與資訊順序。
- 偏好與回饋迴路造成同溫層、資訊偏差與比較困難。
- 使用者難以理解「為什麼這則結果排在第一」。

另一方面，當使用者搜尋與自我傷害、自殺或嚴重情緒困擾相關的內容時，搜尋結果可能包含危險或觸發性的資訊。搜尋系統若只顧及相關度，可能錯過一個立即提供協助的機會。

本專案因此設計一個「刻意不做個人化」的搜尋引擎，並在偵測到敏感查詢時優先提供關懷與求助資源，作為一個可執行、可驗證的教學示範。

### 1.2 專案目標

1. 實作一個零外部依賴、可直接執行的搜尋引擎示範。
2. 讓排序結果完全由查詢與文件內容決定，不受使用者偏好影響。
3. 提供偏好設定介面，但明確限制其只影響外觀，並以測試驗證排序不變。
4. 建立敏感關鍵字偵測，涵蓋中文、英文、空白與標點規避寫法。
5. 偵測到高風險查詢時，立即顯示關懷頁面、求助步驟與台灣求助專線。
6. 提供透明可驗證的說明頁與 JSON API。
7. 以自動化測試驗證非個人化排序、敏感偵測、HTML 跳脫與主要路由。

### 1.3 專案範圍

本專案聚焦於：

- 單一靜態文件集（24 篇）的關鍵字搜尋。
- TF-IDF 餘弦相似度排序。
- 偏好設定的外觀呈現（主題、密度、是否顯示分數）。
- 自殺、自我傷害、傷害他人、情緒困擾與身體困擾的關鍵字偵測。
- 台灣地區的求助與緊急資源。

不包含：帳號系統、搜尋紀錄、機器學習排序、網頁爬蟲、資料庫、多語系、廣告或即時個人化。


依賴方向刻意保持單向：

- `search/rank.js` 只依賴 `search/tokenize.js` 與索引物件，不依賴 HTTP、Cookie、偏好或視圖。
- `safety/detect.js` 只依賴 `safety/keywords.js`，不依賴排序或資料庫。
- `routes/*` 負責組合搜尋、偵測與視圖，是唯一知道「使用者偏好」的層級。
- `views/*` 只負責輸出 HTML，所有動態文字都經過 `esc()`。
- `http.js` 與 `router.js` 為基礎設施，不包含業務邏輯。

這樣的依賴方向讓「排序不受偏好影響」不只是口號，而是可由程式結構檢查的性質：排序模組根本拿不到偏好資料。

## 4. 非個人化搜尋演算法

### 4.1 設計原則

排序函式 `rankDocuments(query, index)` 的輸入只有兩個：

1. `query`：使用者輸入的查詢字串。
2. `index`：由靜態文件集建立的索引。

函式簽章中沒有使用者物件、偏好、Cookie、Session、歷史紀錄、位置或時間。因此從程式結構上就無法因為偏好而改變排序。偏好只在路由層被讀取，用於版面呈現，不會傳入 `rankDocuments`。

### 4.2 文字切分

- 先以 `String.prototype.normalize('NFKC')` 正規化，並轉為小寫。
- 英文與數字以 `[a-z0-9]+` 切分為單詞。
- 中文（CJK）以相鄰二字詞（bigram）切分。例如「資料庫」切成「資料」「料庫」；「機器學習」切成「機器」「器學」「學習」。
- 單一中文字則保留為單字詞。

使用 bigram 的原因是在不引入斷詞套件的前提下，仍能對中文查詢提供合理的詞彙匹配。

### 4.3 TF-IDF 索引

文件中的四個欄位有固定權重：

| 欄位 | 權重 |
|------|------|
| title | 3 |
| tags | 2 |
| category | 2 |
| content | 1 |

對每篇文件，先計算每個詞的加權詞頻 TF，再依全體文件計算逆文件頻率：

```text
IDF(t) = ln((N + 1) / (df(t) + 1)) + 1
```

其中 `N` 為文件總數，`df(t)` 為包含詞 `t` 的文件數。文件向量正規化為單位長度，以避免長文件僅因字數多而取得不公平的優勢。

### 4.4 餘弦相似度與排序

查詢也轉為 TF-IDF 向量，並與每篇文件計算餘弦相似度：

```text
score(q, d) = (q · d) / (|q| × |d|)
```

排序規則：

1. 分數由高到低。
2. 分數相同時，依 `document.id` 由小到大排序。

第二條規則是固定的字典序，不使用時間、隨機數或任何外部狀態，因此相同查詢與相同文件集會產生完全相同的順序。這也讓測試可以穩定比較結果。

### 4.5 明確不使用的資料

以下資料不會進入索引或排序：

- 使用者偏好設定（主題、密度、是否顯示分數）。
- 瀏覽紀錄、搜尋歷史、點擊行為。
- 地理位置、裝置、瀏覽器、作業系統。
- 時間、熱門度、廣告、推薦分數。
- 帳號、身分、個人檔案。
- 任何即時回饋或 A/B 測試分組。

### 4.6 如何驗證非個人化

系統提供三種驗證方式：

1. **程式結構**：`rankDocuments(query, index)` 沒有偏好參數。
2. **API 標記**：`/api/search` 固定回傳 `personalization: false` 與 `preferencesUsed: false`。
3. **自動化測試**：以兩個不同的 `prefs` Cookie 呼叫 `/api/search?q=健康`，比較結果的 id 與分數，兩者必須完全相同。

此外，結果頁會顯示「排序不受偏好影響」的提示，並列出目前偏好只影響外觀。演算法說明頁也公開完整公式與同分規則。

### 4.7 設計取捨

非個人化的代價是無法針對個別使用者調整結果，也無法利用點擊回饋改善排序。但換來的是：

- 可預測、可比較、可稽核的結果。
- 不同使用者對同一問題能看到相同的資訊順序。
- 較低的隱私風險與較少的偏誤來源。

對本專案而言，這種取捨符合「公平、透明、以人為本」的目標。

### 4.8 範例：以「資料庫」說明排序

假設使用者查詢「資料庫」，切分後得到兩個詞：`資料`、`料庫`。

1. 系統先找出索引中含有這兩個詞的文件，例如：
   - `doc-001`：標題「資料庫系統入門」，標題同時命中 `資料` 與 `料庫`。
   - `doc-002`：內容提到「資料庫」，內容命中兩個詞。
   - `doc-014`：內容提到「資料庫」，內容命中兩個詞。
2. 標題權重為 3、內容權重為 1，因此 `doc-001` 的 TF 明顯較高。
3. 再乘上 IDF 並做長度正規化，得到每篇文件的餘弦相似度。
4. 依分數由高到低排序，因此 `doc-001` 排在第一位。
5. 若兩篇文件分數完全相同，則比較 `document.id`，由小到大排序。

這個例子說明了三件事：

- 排序只使用查詢與文件欄位，不需要知道使用者是誰。
- 權重是固定常數，不會因偏好或歷史而改變。
- 同分規則也是固定的，因此結果可重現。

## 5. 敏感搜尋與即時關懷

### 5.1 關鍵字分類

`safety/keywords.js` 將關鍵字分為五類：

| 分類 | 嚴重度 | 例子 |
|------|--------|------|
| suicide（自殺或結束生命的念頭） | critical | 自殺、輕生、想死、活不下去、kill myself、want to die |
| self_harm（自我傷害） | critical | 自殘、割腕、傷害自己、自我傷害、self-harm、hurt myself |
| harm_others（傷害他人） | critical | 想殺人、傷害別人、報復社會、kill someone |
| severe_distress（嚴重情緒困擾） | concern | 憂鬱、抑鬱、絕望、撐不下去、panic attack |
| physical（身體健康困擾） | concern | 不吃不喝、催吐、暴食、失眠、睡不著 |

只要命中任一關鍵字即視為 `flagged`。若包含 critical 分類，嚴重度為 `critical`；否則為 `concern`。

### 5.2 正規化與去混淆

為了降低「自 殺」「自-殺」「自　殺」等規避寫法造成的漏判，偵測前會：

1. 以 NFKC 正規化（處理全形／半形與相容字元）。
2. 轉為小寫。
3. 建立兩種比對字串：
   - `spaced`：保留空白，供英文片語比對。
   - `compact`：移除所有非字母、非數字、非 CJK 字元，供中文比對。

英文關鍵字使用詞邊界比對，避免 `die` 誤匹配 `diet` 這類子字串問題；中文關鍵字則在 `compact` 字串中比對。

### 5.3 降低誤判

關鍵字法容易產生誤判，因此加入少量排除詞：

- 「想死你了」「想死妳」「想死您」「想死我」：中文的「很想念」用法。
- 「不想活動」「不想活动」：不是「不想活」。
- 「自殺式」「自殺炸彈」「自殺突擊隊」：新聞、電影或攻擊類型。
- 「傷害自己人」：不是自我傷害。
- 「絕食抗議」：社會運動，不是身體困擾。
- 「憂鬱的熱帶」：書名。

這些排除詞會在中文 `compact` 字串中先被替換為空白，再進行比對。這不能完全消除誤判，但能降低常見的明顯誤判。相關限制會在後續章節說明。

### 5.4 嚴重度與顯示流程

```text
使用者送出查詢
        │
        ▼
   安全偵測 detectSafety(query)
        │
        ├── 未命中 ──────────────► 一般搜尋結果頁
        │
        ├── concern ─────────────► 關懷橫幅 + 搜尋結果
        │
        └── critical
              ├── 未確認 ────────► 全頁關懷頁（不顯示結果）
              └── ack=1 ─────────► 關懷橫幅 + 搜尋結果
```

- **critical 未確認**：顯示全頁關懷頁，內容包含同理訊息、現在可以做的事、求助專線與緊急提示。一般結果不會出現在頁面上。
- **critical 已確認**：使用者按下「我了解，繼續查看結果」後，以 `ack=1` 重新請求；此時顯示結果，但關懷橫幅仍保留在結果上方。
- **concern**：不阻擋結果，但在結果上方顯示關懷橫幅與求助連結。

這樣的設計兼顧「立即關心」與「不剝奪使用者取得資訊的權利」。系統不會強迫使用者停留在關懷頁，但會確保求助資源在敏感查詢中始終可見。

### 5.5 求助資源

`src/safety/resources.js` 集中管理資源，避免各頁面重複維護：

| 資源 | 電話 | 說明 |
|------|------|------|
| 1925 安心專線 | 1925 | 衛生福利部心情支持與危機諮詢，24 小時 |
| 1995 生命線協談專線 | 1995 | 傾聽、陪伴與自殺防治，24 小時 |
| 1980 張老師專線 | 1980 | 情緒、人際與家庭議題諮詢 |
| 113 保護專線 | 113 | 家庭暴力、性侵害、兒少保護，24 小時 |
| 119 緊急救護 | 119 | 立即生命危險或身體傷害 |
| 110 報警 | 110 | 人身安全威脅或需要警方協助 |

關懷頁與求助頁也提供「現在可以做的事」步驟，包括確保安全、聯絡信任的人、撥打專線、就醫，以及立即危險時撥打 119 或 110。

### 5.6 設計原則

- **先關心，再提供資訊**：高風險查詢不直接落入一般結果頁。
- **不重複查詢原文**：關懷頁只描述偵測到的分類，不把可能觸發的關鍵字再次放大顯示。
- **不阻斷使用者**：提供確認後繼續查看的選項，尊重使用者自主。
- **資源可立即使用**：電話號碼以 `tel:` 連結呈現，行動裝置可直接撥打。
- **一致性**：所有使用者遇到相同敏感查詢時，都會看到相同的關懷流程，不因偏好而不同。

### 5.7 敏感詞庫的維護原則

敏感詞庫不是一般關鍵字表，它會直接影響使用者是否看到求助資源，因此需要更謹慎的維護流程：

1. **專業審閱**：新增或移除 critical 關鍵字前，應由心理或醫療專業人員審閱，避免過度標記或漏接。
2. **版本控制**：每次調整詞庫都應記錄原因、日期與影響範圍，方便回溯。
3. **誤判回報**：提供管道讓使用者回報誤判，例如「公司活不下去」被標記為自殺風險。
4. **避免羞辱性文字**：詞庫只用於偵測與提供協助，不用於標記使用者或公開展示。
5. **定期測試**：每次調整後重新執行敏感偵測測試，確認規避寫法與誤判排除仍然有效。
6. **地區差異**：求助專線與用語需依地區調整，不能直接套用到其他國家。

本專案的詞庫是教學示範版本，尚未經過臨床驗證；正式系統應以更嚴謹的流程維護。

## 6. 功能實作

### 6.1 首頁

- 顯示專案主張：「同樣的查詢，每個人看到同樣的結果。」
- 提供大型搜尋框與範例查詢。
- 三張特色卡片：非個人化排序、敏感搜尋即時關懷、透明可驗證規則。
- 顯示索引文件數、分類數與「0 個個人化訊號」。
- 提供四個主要求助專線與緊急提示。

### 6.2 搜尋結果頁

- 顯示查詢字串、結果數量與排序依據。
- 若查詢被標記為 concern 或已確認的 critical，顯示關懷橫幅。
- 顯示「排序不受偏好影響」提示與目前偏好。
- 每筆結果包含標題、分類、摘要、標籤與相似度分數。
- 可展開「為什麼會看到這則結果？」，查看命中詞與完整分數。
- 無結果時顯示替代建議。

### 6.3 關懷頁

- 標題：「你不需要一個人面對。」
- 同理訊息，不明確重複使用者的敏感查詢。
- 兩個主要按鈕：撥打 1925、撥打 1995。
- 「現在可以做的事」步驟清單。
- 完整求助專線卡片。
- 緊急提示：立即危險請撥 119 或 110。
- 「我了解，繼續查看結果」與「回到首頁」選項。

### 6.4 偏好設定

- 可設定主題（淺色／深色）、結果密度（寬鬆／緊湊）、是否顯示分數。
- 偏好儲存在 `prefs` Cookie 中，伺服器只將其用於版面呈現。
- 頁面明確說明：「這裡的設定只改變外觀。」
- 提供 `/api/search?q=健康` 連結，讓使用者自行驗證排序不變。

### 6.5 演算法說明頁

- 列出「會影響排序」與「不會影響排序」的資料。
- 說明文字切分、TF-IDF、餘弦相似度與同分規則。
- 公開公式與 API 標記。
- 說明敏感搜尋的處理方式與關鍵字法的限制。
- 說明隱私設計：不建立帳號、不記錄查詢、不持久化搜尋內容。

### 6.6 求助資源頁

- 集中列出 24 小時與主要專線。
- 分別提供「有傷害自己的念頭」「被情緒淹沒」「身體持續不適」的因應步驟。
- 提供「如何陪伴身邊的人」與「什麼時候該就醫」的指引。
- 所有頁面底部都有緊急提示。

### 6.7 JSON API

`GET /api/search?q=關鍵字[&ack=1]`

回應範例：

```json
{
  "query": "健康",
  "algorithm": "tf-idf-cosine-v1",
  "personalization": false,
  "preferencesUsed": false,
  "safety": {
    "flagged": false,
    "severity": "none",
    "blocked": false,
    "acknowledged": false,
    "categories": [],
    "matches": []
  },
  "results": [
    {
      "id": "doc-010",
      "title": "均衡飲食與日常營養",
      "category": "健康",
      "tags": ["飲食", "營養", "健康", "水分"],
      "snippet": "……",
      "score": 0.31,
      "matchedTerms": ["健康"]
    }
  ]
}
```

高風險查詢在未確認時，`safety.blocked` 為 `true`，`results` 為空陣列；加上 `ack=1` 後才會回傳結果。

### 6.8 頁面與資料流

```text
GET /search?q=...
        │
        ├── 讀取 q（只取查詢字串）
        ├── 讀取 prefs Cookie（只用於外觀）
        ├── detectSafety(q)
        │      ├── 未命中 ──────────────┐
        │      ├── concern ─────────────┤
        │      └── critical ──┐         │
        │                     │         │
        │              未 ack？│         │
        │                ├── 是 → 關懷頁（不排序）
        │                └── 否 ─────────┤
        │                                ▼
        └── rankDocuments(q, index) → 結果頁（必要時加關懷橫幅）
```

偏好資料流與排序資料流是分開的：

```text
Cookie prefs ──► parsePreferences ──► layout（主題、密度、分數顯示）
Query q      ──► rankDocuments ─────► 結果排序與分數
```

兩條線在路由層交會，但偏好不會被傳入 `rankDocuments`。這是本專案最重要的架構限制。

## 8. 安全性與隱私

### 8.1 XSS 防護

所有使用者輸入與文件內容在輸出至 HTML 前都經過 `esc()` 跳脫：

- `&` → `&amp;`
- `<` → `&lt;`
- `>` → `&gt;`
- `"` → `&quot;`
- `'` → `&#39;`

查詢字串會出現在頁面標題、結果數量與確認連結中，因此也必須跳脫。測試包含 `<script>alert(1)</script>` 查詢，確認輸出不會產生原始 script 標籤。

### 8.2 Content Security Policy

HTML 回應加上：

```text
default-src 'self'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
```

本專案不使用行內 script 或行內樣式，因此可以採用較嚴格的 CSP。另加上 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY` 與 `Referrer-Policy: same-origin`。

### 8.3 請求與靜態資源

- 請求本文上限為 64 KB，避免過大請求耗盡記憶體。
- 靜態資源路徑以 `path.resolve()` 正規化，並檢查是否位於 `public` 目錄內，防止路徑穿越。
- 只提供已知副檔名的 Content-Type。

### 8.4 隱私

- 不建立使用者帳號。
- 不記錄查詢日誌。
- 不將查詢內容寫入檔案或資料庫。
- 偏好只存在瀏覽器 Cookie，用於外觀呈現。
- 文件集為靜態 JSON，不包含個人資料。

### 8.5 已知安全限制

- 偏好 Cookie 沒有簽章，使用者可以自行修改；但偏好只影響外觀，不影響排序或安全偵測。
- 關鍵字偵測可能被刻意規避，也可能產生誤判。
- 未實作速率限制、HTTPS 終止與 WAF；正式部署需搭配反向代理與 TLS。

5. 搜尋「失眠」等 concern 關鍵字時，會直接顯示結果與關懷橫幅。

## 11. 已知限制

1. **關鍵字法無法理解語意**：可能漏判隱喻、反諷或間接表達，也可能誤判一般用法。
2. **排除詞只能降低部分誤判**：無法涵蓋所有情境，例如「公司活不下去」仍可能被標記。
3. **中文僅使用 bigram**：未使用專業斷詞，少數詞彙邊界可能不理想。
4. **靜態文件集**：不支援即時新增、刪除或更新文件，需重新啟動才能重建索引。
5. **無分頁**：目前一次顯示所有結果；文件量大時需加入分頁。
6. **無搜尋紀錄與帳號**：無法提供個人化，也無法跨裝置同步偏好。
7. **偏好 Cookie 無簽章**：使用者可自行修改，但因只影響外觀，風險有限。
8. **無速率限制**：正式部署需加入請求頻率限制。
9. **無 HTTPS**：需由反向代理提供 TLS。
10. **求助資源以台灣為主**：其他地區使用者需自行查找當地資源。
11. **不是醫療或危機處理系統**：本系統只提供資訊與資源連結，不能取代專業協助。
12. **未實作多語系**：介面固定為繁體中文。

## 12. 未來改進方向

1. **語意偵測**：加入可解釋的語意模型或規則，降低關鍵字法的漏判與誤判。
2. **多語系資源**：依使用者地區提供當地求助專線。
3. **分頁與效能**：支援大量文件與增量索引。
4. **可設定的敏感詞庫**：由專業人員維護與審閱，並記錄版本。
5. **更細緻的嚴重度**：區分「求助意圖」與「立即風險」，提供不同層級的關懷。
6. **無障礙與國際化**：加入更多語系、鍵盤操作與螢幕閱讀器測試。
7. **稽核與透明度報告**：公開演算法版本、測試結果與敏感詞庫變更紀錄。
8. **離線與校園部署**：打包為校園內網可用的服務，並與校園諮商資源整合。
9. **安全強化**：加入速率限制、HTTPS、Cookie 簽章與 CSP 報告。
10. **使用者研究**：與心理專業人員合作，驗證關懷頁的文字與流程是否合適。

## 13. 結論

本專案實作了一個刻意「不做個人化」的搜尋引擎，並將敏感搜尋的關懷流程放在排序之前。主要成果包括：

- 以 TF-IDF 餘弦相似度建立可解釋、可重現、非個人化的排序。
- 以固定同分規則與 API 標記，讓「排序不受偏好影響」成為可驗證的承諾。
- 以正規化、去混淆與排除詞，建立涵蓋中英文的敏感關鍵字偵測。
- 在 critical 查詢時先顯示關懷頁，concern 查詢時顯示關懷橫幅，並保留使用者繼續查看結果的選擇。
- 集中管理台灣求助資源，讓關懷頁、求助頁與首頁使用一致資訊。
- 以 25 項自動化測試驗證排序、偵測、路由、XSS 與錯誤處理。

本專案的價值不在於取代真實搜尋引擎或專業危機服務，而在於示範一種設計立場：搜尋系統可以在追求相關度的同時，選擇公平、透明與照顧使用者。當技術選擇涉及人的資訊取得與安全時，演算法不只是效率問題，也是倫理問題。
