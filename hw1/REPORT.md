# minicurl 專案報告

## 摘要

本專案以 Node.js 實作一個類似 `curl` 的命令列 HTTP 用戶端，命名為 `minicurl`。程式完全不使用任何外部套件，只依賴 Node.js 內建的 `http`、`https`、`fs`、`url` 與 `node:test` 等模組。`minicurl` 支援常見的 HTTP 方法、自訂標頭、表單與 JSON 請求本文、基本驗證、重新導向跟隨、輸出至檔案、逾時控制與詳細模式，並具備對應的結束碼與自動化測試。

本報告說明專案的動機、需求、系統架構、各模組的實作方式、測試策略與結果，以及目前已知限制與未來改進方向。

---

## 1. 專案簡介

### 1.1 專案動機

`curl` 是軟體開發與系統維運中最常使用的工具之一，用來送出 HTTP 請求、檢查 API、下載檔案與除錯網路服務。透過自行實作一個簡化版的 `curl`，可以深入理解：

- HTTP 請求與回應的組成（請求行、標頭、本文、狀態碼）
- TCP/TLS 連線在程式語言中的抽象方式
- 命令列工具的參數設計與使用者體驗
- 重新導向、逾時、錯誤處理等實務議題
- 如何為命令列程式撰寫可靠的自動化測試

### 1.2 專案目標

1. 以 Node.js 內建模組實作可直接執行的命令列 HTTP 用戶端。
2. 支援 `curl` 最常用的選項，降低學習與轉換成本。
3. 不需要安裝任何第三方套件即可執行與測試。
4. 具備清楚的模組分工，方便閱讀、維護與擴充。
5. 以自動化測試驗證主要功能與邊界情況。

### 1.3 專案範圍

本專案聚焦於「單次 HTTP 請求的送出與結果輸出」，不處理瀏覽器等級的功能（例如 JavaScript 執行、Cookie 管理、快取），也不支援 HTTP/2、代理伺服器、檔案續傳與 FTP 等進階協定。

| 項目 | 內容 |

| 程式語言 | JavaScript（ES Modules） |
| HTTP 實作 | `node:http`、`node:https` |
| 測試框架 | `node:test` 內建測試執行器 |
| 外部依賴 | 無 |

### 2.1 為何選擇 Node.js

- 內建完整的 HTTP/HTTPS 客戶端，不需要額外依賴。
- 事件驅動與非同步 I/O 模型適合網路程式。
- 跨平台，Windows、macOS、Linux 皆可直接執行。
- ES Modules 與 `node:test` 讓專案結構現代化且測試方便。

### 2.2 為何不使用第三方套件

本專案目的是理解 HTTP 工具的原理。若使用 `axios`、`node-fetch` 或 `commander` 等套件，將遮蔽請求流程與參數解析的核心概念。因此所有功能皆以標準庫從頭實作，也讓專案具備「下載即可執行」的特性。

## 4. 系統架構

### 4.1 檔案結構

```text
hw1/
├── bin/
│   └── minicurl.js          # 命令列入口
├── src/
│   ├── parse-args.js        # 參數解析與說明文字
│   ├── client.js            # HTTP/HTTPS 請求與重新導向
│   └── run.js               # 請求建構、輸出與錯誤處理
├── test/
│   └── minicurl.test.js     # 自動化測試
├── package.json
└── REPORT.md
```

### 4.2 模組關係

```text
                 process.argv
                      │
                      ▼
              bin/minicurl.js
                      │
                      ▼
                 src/run.js ──────────────► src/parse-args.js
                      │
                      ├───────────────────► src/client.js
                      │                          │
                      │                          ├──► node:http
                      │                          └──► node:https
                      │
                      ├───────────────────► node:fs
                      └───────────────────► stdout / stderr
```

### 4.3 模組職責

| 模組 | 職責 |
|------|------|
| `bin/minicurl.js` | 取得命令列參數、呼叫 `run()`、設定 `process.exitCode` |
| `src/parse-args.js` | 解析短選項、長選項、`--opt=value`、合併短旗標、錯誤與說明 |
| `src/client.js` | 建立請求、送出本文、收集回應、處理逾時與重新導向 |
| `src/run.js` | 依選項建構請求、決定輸出位置、轉換錯誤為結束碼 |

### 4.4 請求處理流程

1. `bin/minicurl.js` 將 `process.argv.slice(2)` 傳入 `run()`。
2. `parseArgs()` 將參數轉為結構化選項物件，並收集 URL 清單。
3. 若為 `--help` 或 `--version`，直接輸出並結束。
4. `buildRequest()` 依選項決定方法、標頭與本文：
   - 有資料時預設方法為 POST。
   - `--json` 設定 JSON 內容類型。
   - `-u` 產生 Basic 驗證標頭。
5. 對每個 URL 呼叫 `performRequest()`。
6. `sendOnce()` 建立 `http.request` 或 `https.request`，送出請求並收集回應。
7. 若啟用 `-L` 且收到重新導向狀態，計算新網址並視情況改為 GET。
8. `run()` 依 `-i`、`-I`、`-o` 決定輸出內容與位置。
9. 依錯誤類型或 `-f` 設定結束碼。

## 5. 實作說明

### 5.1 參數解析（`src/parse-args.js`）

參數解析採用手寫的狀態機式迴圈，主要處理以下形式：

| 形式 | 範例 |
|------|------|
| 短選項加值 | `-X POST` |
| 短選項緊貼值 | `-XPOST`、`-H"Accept: */*"` |
| 長選項加值 | `--header "Accept: */*"` |
| 長選項等號 | `--max-time=5` |
| 合併布林短旗標 | `-sL`、`-ik` |
| 選項結束符 | `--` 之後全部視為 URL |
| 重複資料 | `-d a=1 -d b=2` |

解析結果為一個選項物件，包含方法、標頭陣列、資料片段陣列、輸出檔名、各布林旗標與 URL 陣列。若遇到未知選項、缺少參數或非法數值，會拋出 `UsageError`，由 `run()` 轉為結束碼 2。

重複的 `-d` 會先收集到 `dataParts`，稍後以 `&` 串接，行為與 `curl` 一致。重複的 `-H` 則保留為陣列，於建構請求時設定；同名標頭以最後一次為準。

### 5.2 請求建構（`src/run.js`）

`buildRequest()` 負責將選項轉為實際請求：

1. **標頭解析**：將 `-H` 的每個字串以第一個冒號切割為名稱與值，名稱或格式不合法時回報參數錯誤。
2. **方法決定**：
   - 有 `-I` 時使用 `HEAD`。
   - 有 `-X` 時使用指定方法（轉為大寫）。
   - 否則若包含資料或 `--json`，使用 `POST`；其餘使用 `GET`。
3. **本文決定**：資料片段以 `&` 串接。`HEAD` 不送出本文。
4. **內容類型**：
   - `--json` 且未指定時設定 `application/json`。
   - 有表單資料且未指定時設定 `application/x-www-form-urlencoded`。
   - 若使用者以 `-H` 指定，則尊重使用者設定。
5. **驗證與其他標頭**：
   - `-u` 以 Base64 編碼 `user:pass`，設定 `Authorization: Basic ...`。
   - `-A` 與 `--referer` 分別設定 `User-Agent` 與 `Referer`。
   - 已存在同名標頭時不覆寫使用者的設定（驗證標頭）。

### 5.3 HTTP 客戶端（`src/client.js`）

#### 5.3.1 單次請求

`sendOnce()` 使用 `new URL()` 解析網址，依據協定選擇 `http` 或 `https` 模組，並以 Promise 包裝非同步請求。重點如下：

- **Content-Length**：有本文且使用者未指定時，以 `Buffer.byteLength()` 自動計算。
- **逾時**：`req.setTimeout()` 在超過 `--max-time` 時 destroy 請求，並標記 `ETIMEDOUT`。
- **TLS**：`-k` 時設定 `rejectUnauthorized: false`。
- **詳細模式**：將請求行、請求標頭、回應狀態行與回應標頭輸出到 stderr，並以 `>` 與 `<` 區分方向。
- **統一回應物件**：包含狀態碼、狀態訊息、HTTP 版本、標頭、原始標頭、本文 Buffer 與耗時。

回應本文以 chunk 陣列收集後合併為 Buffer，對一般 API 與網頁已足夠；此設計的取捨見「已知限制」。

#### 5.3.2 重新導向

`performRequest()` 以迴圈處理重新導向，最多 10 次，避免無限迴圈。規則如下：

- 只有啟用 `-L` 且狀態碼為 301、302、303、307、308，且回應含 `Location` 時才跟隨。
- 以 `new URL(location, currentUrl)` 解析相對或絕對位址。
- **303**：一律改為 GET（HEAD 仍為 HEAD），並移除本文。
- **301/302**：若非 GET/HEAD，改為 GET 並移除本文，符合常見瀏覽器與 `curl` 行為。
- **307/308**：保留原方法與本文。
- 每次重新送出時由 `sendOnce()` 重新計算 `Content-Length`，避免舊標頭殘留。

### 5.4 輸出與錯誤處理（`src/run.js`）

- **一般輸出**：回應本文寫入 stdout。
- **`-i`/`-I`**：先輸出狀態行與原始回應標頭，再輸出本文；`-I` 會自動包含標頭。
- **`-o`**：將上述內容寫入指定檔案，成功時不輸出到 stdout。
- **`-f`**：狀態碼大於等於 400 時不輸出本文，改以結束碼 22 結束。
- **錯誤訊息**：連接失敗、逾時、憑證錯誤等會輸出到 stderr，並對應不同結束碼。
- **多 URL**：依序處理，任何一個失敗會記錄結束碼；後續 URL 仍會繼續處理。

### 5.5 命令列入口（`bin/minicurl.js`）

入口檔僅負責呼叫 `run()` 並設定 `process.exitCode`。使用 top-level await 讓程式在非同步請求完成後才結束，避免過早退出。

## 6. 測試

### 6.1 測試策略

測試檔 `test/minicurl.test.js` 採用三層策略：

1. **真實 HTTP 伺服器**：以 `http.createServer()` 啟動監聽隨機埠的本機伺服器，提供 `/hello`、`/echo`、`/redirect`、`/status/404`、`/slow` 等路由。
2. **真實子行程**：以 `child_process.spawn()` 執行 `bin/minicurl.js`，確保測試涵蓋參數解析、網路請求與輸出流程，而非只測試單一函式。
3. **非同步等待**：測試以 Promise 等待子行程關閉並收集 stdout、stderr 與結束碼，避免阻塞事件迴圈造成伺服器無法回應。

測試伺服器於 `before()` 啟動、`after()` 關閉，使用動態埠避免連接埠衝突。

### 6.2 測試案例

| 編號 | 測試項目 | 驗證重點 |

| 3 | `-d` 表單 | 預設 POST、本文與內容類型 |

## 7. 與 curl 的比較

| 項目 | curl | minicurl |
|------|------|----------|
| 語言 | C | JavaScript（Node.js） |
| 外部依賴 | 需編譯安裝 | 無，需 Node.js 執行環境 |
| 基本請求 | 支援 | 支援 |
| 自訂方法與標頭 | 支援 | 支援 |
| 表單與 JSON | 支援 | 支援（`-d`、`--json`） |
| 重新導向 | 支援 | 支援（最多 10 次） |
| 基本驗證 | 支援 | 支援 |
| 輸出檔案 | 支援 | 支援 |

| 檔案上傳與續傳 | 支援 | 不支援 |
| 進度條 | 支援 | 不支援 |

`minicurl` 的定位是「教學用簡化版」，重點在理解原理與常見 API 測試，而非取代完整的 `curl`。

## 8. 已知限制

1. **回應完全緩衝於記憶體**：目前會先收集完整回應再輸出，不適合極大檔案。可改為串流寫入 stdout 或檔案。
2. **不支援 Cookie**：未實作 Cookie 儲存與傳送，無法維持登入狀態。
3. **不支援代理伺服器**：未實作 `HTTP_PROXY`/`HTTPS_PROXY` 或 `--proxy`。
4. **不支援 HTTP/2 與 HTTP/3**：僅使用 Node.js 的 HTTP/1.1 模組。
5. **不支援檔案上傳與續傳**：未實作 multipart/form-data、`--data-binary` 或 `-C`。
6. **同名標頭會被覆寫**：標頭以物件儲存，重複同名標頭只保留最後一個。
7. **多 URL 搭配 `-o` 會覆寫**：尚未支援 `#1` 之類的檔名樣板。
8. **進度顯示從簡**：僅提供 `-v` 詳細模式，沒有進度條或速率統計。
9. **不支援 `-G`、`--url-query` 等查詢字串選項**：需自行將參數放入 URL。
10. **重新導向的敏感標頭**：跨網域重新導向時仍會保留 `Authorization`，與部分安全實作不同，需注意使用情境。

## 9. 未來改進方向

1. **串流輸出**：將回應直接 pipe 到 stdout 或檔案，降低記憶體使用。
2. **Cookie 管理**：實作簡易 Cookie jar 與 `-b`/`-c` 選項。
3. **代理與憑證**：支援代理伺服器、CA 憑證檔與客戶端憑證。
4. **多部分表單**：支援 `-F` 與檔案上傳。
5. **重試機制**：針對暫時性錯誤提供 `--retry`。
6. **更完整的標頭模型**：以陣列保留重複標頭，例如多個 `Set-Cookie`。
7. **結構化輸出**：提供 JSON 格式的請求統計，方便自動化。
8. **平行請求**：支援多 URL 並行處理與結果彙整。
9. **套件化**：發佈至 npm，提供 `npx minicurl` 使用方式。
10. **更完整的測試**：加入 TLS、proxy、大檔案與跨平台路徑測試。

## 10. 心得與結論

本專案以不到數百行的程式碼，實作了一個具備實用功能的 `curl` 簡化版。過程中進行了以下學習：

- **HTTP 協定的具體化**：從課本上的請求行、標頭與狀態碼，變成實際可送出與解析的程式。
- **非同步程式設計**：以 Promise 包裝事件式 API，讓請求流程易讀且可測試。
- **命令列工具設計**：參數別名、等號形式、合併短旗標與清楚的錯誤訊息，都是良好使用者體驗的一部分。
- **重新導向的細節**：不同狀態碼對方法與本文的處理規則不同，必須分別實作。
- **測試的重要性**：透過本機伺服器與子行程測試，可以在不依賴外部網路的情況下驗證整體行為。

整體而言，`minicurl` 已達成專案目標：零外部依賴、功能實用、架構清楚且具備自動化測試。它不僅是一個可用的命令列工具，也是理解 HTTP 與命令列程式設計的良好教材。未來可依「已知限制」與「未來改進方向」逐步擴充，使其更接近真實 `curl` 的能力。
